# Personal Knowledge Hub — дизайн проекта

_Дата: 2026-10-25 · Статус: согласован_

## 1. Цель и требования

Сервис для сбора внешнего контента: статьи, ссылки, заметки, фрагменты кода и документы. Система индексирует их и позволяет быстро находить нужное.

> Пример: читаешь статью об Azure Service Bus, сохраняешь ссылку, добавляешь заметку — через несколько месяцев находишь её по ключевым словам или содержимому.

**Основные функции:**
- REST API для создания и управления записями.
- Теги, коллекции и полнотекстовый поиск.
- Автоматическое извлечение содержимого веб-страниц.
- Обработка загруженных документов в фоне.
- Поиск по тексту, в дальнейшем — по смыслу.
- Напоминания о сохранённых материалах (ручные по дате + дайджест).
- Экспорт данных.

**Ограничения и решения:**
| Параметр | Решение |
|---|---|
| Платформа | Облако Azure |
| Пользователи | Несколько, у каждого своя изолированная база |
| Бэкенд | .NET (C#) |
| Клиенты | REST API + веб (SPA) + Telegram-бот |
| Поиск | Полнотекстовый сейчас, смысловой позже (без переделки архитектуры) |
| Напоминания | Ручные по дате + дайджест (непрочитанное, «год назад», ближайшие напоминания); каналы Telegram и Email |
| Экспорт | ZIP: Markdown с YAML-метаданными + исходные файлы + `export.json` |
| Коллекции | Плоские, запись может быть в нескольких коллекциях |
| Бюджет | ~$15–60/мес |

**Вне первой версии (YAGNI):** смысловой поиск, общий доступ к записям, вложенные коллекции, браузерное расширение, мобильное приложение, staging-окружение, интервальные повторения.

## 2. Рассмотренные альтернативы

Цены — Azure Retail Prices API, регион East US, октябрь 2026.

### Хранилище и поиск — выбран PostgreSQL

| Вариант | ≈ $/мес | Итог |
|---|---|---|
| **PostgreSQL Flexible Server B1ms** | ~16 (вычисления $0.017/ч ≈ $12.4 + хранилище) | **Выбран.** Одна база: данные, FTS (RU/EN), очередь задач; смысловой поиск позже через `pgvector` |
| Azure SQL Database Serverless | 0–175 | Отклонён: $0.52 за vCore-час, бесплатно ~55 ч/мес на 0.5 vCore. Фоновые задачи и планировщик не дают базе засыпать → цена непредсказуема; холодный старт после паузы |
| Cosmos DB + Azure AI Search | ~74 | Отклонён: AI Search Free (~50 МБ) не хватит, Basic ≈ $74/мес — выше бюджета; два сервиса нужно синхронизировать; изоляция пользователей только фильтром в каждом запросе |

### Хостинг бэкенда — выбран App Service

| Вариант | ≈ $/мес | Итог |
|---|---|---|
| **App Service Linux B1, модульный монолит** | 12.4 | **Выбран.** Без холодных стартов, один процесс, простой деплой |
| Azure Container Apps (consumption) | 0–14 | Отклонён: холодные старты (в т.ч. для бота), Docker и больше инфраструктуры |
| Azure Functions Flex Consumption | ~0–5 | Отклонён: логика разбросана по триггерам, холодные старты, REST API на Functions неудобнее |

## 3. Технологии и архитектура

### Ресурсы Azure (~$30/мес)

| Ресурс | Назначение | ≈ $/мес |
|---|---|---|
| App Service Linux B1 | API, SPA, webhook бота, фоновые воркеры — один процесс | 12.4 |
| PostgreSQL Flexible B1ms | Данные, полнотекстовый поиск, очередь задач | ~16 |
| Blob Storage | Документы, архивы экспорта | ~1 |
| Key Vault | Секреты | ~0 |
| Communication Services Email | Напоминания, дайджест | ~0 |
| Application Insights | Логи, ошибки | ~0 в бесплатном объёме |

SPA раздаётся из того же App Service: один деплой, один домен, без CORS, cookie-аутентификация без сложностей.

### Стек

- **Бэкенд:** .NET 10 (LTS), ASP.NET Core Minimal API, EF Core + Npgsql, OpenAPI/Swagger.
- **Фронт:** React + TypeScript + Vite.
- **Поиск:** PostgreSQL FTS — взвешенный `tsvector` (заголовок > теги/заметки > текст), словари `russian` и `english`, GIN-индекс, `websearch_to_tsquery`, `ts_headline`.
- **Извлечение контента:** SmartReader (порт Mozilla Readability), PdfPig (PDF), OpenXML SDK (DOCX).
- **Telegram:** Telegram.Bot, режим webhook.
- **Аутентификация:** встроенная ASP.NET Core — cookie + внешний вход Microsoft/Google (OIDC); персональные API-токены для скриптов. Собственных паролей нет.

### Архитектура — модульный монолит

```
                 ┌──────────────── App Service (один процесс) ───────────────┐
 Браузер (SPA) ─►│  REST API ──► Items / Tags / Collections / Search         │
 Telegram ──────►│  Bot webhook ─┘          │                                │
 Скрипты ───────►│  (API token)             ▼                                │──► PostgreSQL
                 │                   Очередь задач (таблица jobs)            │──► Blob Storage
                 │  Фоновые воркеры: Ingestion · Reminders/Digest · Export   │──► Email / Telegram
                 └───────────────────────────────────────────────────────────┘
```

Сохранение → API сразу отвечает «принято» → воркер в фоне извлекает контент, обновляет поисковый индекс и ставит статус «готово».

## 4. Модули и модель данных

### Модули

| Модуль | Ответственность |
|---|---|
| **Identity** | Вход через Microsoft/Google, пользователи, API-токены, привязка Telegram |
| **Items** | CRUD записей (ссылка, заметка, фрагмент кода, документ), теги, коллекции, отметка «прочитано» |
| **Ingestion** | Фоновое извлечение контента: веб-страницы, PDF, DOCX |
| **Search** | Полнотекстовый поиск, фильтры, подсветка |
| **Reminders** | Напоминания по дате, дайджест; отправка в Telegram/Email |
| **Export** | Сборка ZIP (Markdown + файлы + `export.json`) |
| **Bot** | Webhook Telegram: разбор входящих сообщений, команды |
| **Jobs** | Очередь задач в PostgreSQL (`FOR UPDATE SKIP LOCKED`), повторы, планировщик |

Модули общаются через публичные интерфейсы и не обращаются к чужим таблицам напрямую — это позволит позже вынести, например, Ingestion в отдельный сервис.

### Таблицы

```
users            id, email, display_name, created_at
user_logins      provider, subject, user_id           -- внешние аккаунты (Microsoft/Google)
api_tokens       id, user_id, name, token_hash, expires_at, revoked_at, last_used_at
telegram_links   user_id, chat_id (unique), linked_at

items            id (uuid), user_id, type (link|note|snippet|document),
                 title, url, body,                    -- body: текст заметки / извлечённый текст
                 user_note, code_language,
                 blob_path, content_hash,
                 status (pending|processing|ready|failed), error,
                 read_at,                             -- null = не прочитано
                 search_vector (tsvector), created_at, updated_at
tags             id, user_id, name                    -- unique(user_id, lower(name))
item_tags        item_id, tag_id
collections      id, user_id, name, description      -- плоские
collection_items collection_id, item_id              -- запись может быть в нескольких

reminders        id, user_id, item_id, remind_at, channel, sent_at
user_settings    user_id, timezone, digest_frequency (off|daily|weekly),
                 digest_channels, email
jobs             id, type, payload (jsonb), status, attempts,
                 run_after, locked_until, last_error
exports          id, user_id, status, blob_path, expires_at
```

### Ключевые решения

- **Единая таблица `items`** — поиск, теги, коллекции и напоминания работают одинаково для всех типов; различия — в nullable-полях.
- **`search_vector` пересчитывается в коде** при изменении записи или её тегов (теги в другой таблице, generated column не подходит).
- **Дубликаты:** уникальность `(user_id, url)` для ссылок и `content_hash` для документов — при повторе возвращается существующая запись.
- **Изоляция:** глобальный фильтр EF Core по `user_id` + Row-Level Security в PostgreSQL.
- **API-токены** хранятся только как SHA-256-хэш; токен показывается один раз при создании.
- **Отметка «прочитано»** (`read_at`): кнопка в вебе, `PATCH /api/items/{id}`, inline-кнопка в Telegram-напоминании или дайджесте.
- **Смысловой поиск в будущем:** отдельная таблица `item_chunks (item_id, chunk, embedding vector)` через `pgvector`; текущая схема не меняется.

## 5. Поток данных

### Сохранение ссылки (веб / API)
```
POST /api/items {type: link, url, user_note, tags, collections}
 → валидация URL → проверка дубликата (user_id, url)
 → insert item (status = pending) + job "ingest"
 → 202 Accepted + запись
Воркер: скачивание страницы → SmartReader → title, body
 → пересчёт search_vector → status = ready (или failed + error)
```
Фронт опрашивает статус, пока запись `pending`/`processing`. Заметки и фрагменты кода сохраняются сразу со статусом `ready`.

### Загрузка документа
```
POST /api/items/upload (multipart)
 → проверка размера и типа по сигнатуре → Blob → item (pending) + job
Воркер: PdfPig / OpenXML → body → search_vector → ready
```

### Telegram-бот
- **Привязка:** в вебе «Привязать Telegram» → ссылка `t.me/<bot>?start=<одноразовый код>` (10 минут) → бот сохраняет `chat_id` в `telegram_links`.
- **Входящие:** ссылка → `link`; текст → `note`; файл → `document`. Подпись → `user_note`, хэштеги в ней → теги.
- **Ответы:** «Сохранено» сразу, «Готово: \<заголовок\>» после обработки.
- **Команды:** `/search <запрос>` (топ-5), `/recent`.
- Сообщения от непривязанного `chat_id` не сохраняются — бот отвечает инструкцией по привязке.

### Поиск
```
GET /api/search?q=service bus&type=link&tags=azure&collection=..&from=..&to=..&unread=true
 → websearch_to_tsquery (russian + english) + фильтры + user_id
 → ранжирование ts_rank_cd → подсветка ts_headline → постраничная выдача
```

### Напоминания и дайджест
- Планировщик раз в минуту находит напоминания с `remind_at <= now` и `sent_at IS NULL` → задачи на отправку.
- Дайджест проверяется раз в час: если у пользователя наступило 9:00 по его часовому поясу в выбранный день — собирается подборка (непрочитанное, «сохранено год назад», ближайшие напоминания) и отправляется в выбранные каналы.

### Экспорт
```
POST /api/exports → job → ZIP (Markdown + YAML-метаданные + исходные файлы + export.json)
 → Blob → статус ready → GET /api/exports/{id}/download
```
Архив удаляется через 7 дней.

### Эндпоинты
`/api/items`, `/api/tags`, `/api/collections`, `/api/search`, `/api/reminders`, `/api/exports`, `/api/me` (настройки, API-токены, привязка Telegram), `/telegram/webhook`.

## 6. Обработка ошибок

**Фоновые задачи:**
- До 4 попыток с растущей паузой (1 → 5 → 30 мин); после — `failed`, у записи `status = failed` и понятный текст ошибки. Кнопка «Повторить»: `POST /api/items/{id}/reprocess`.
- Захват задачи на 5 минут (`locked_until`) — после падения процесса задачу подхватит другой воркер.
- Обработчики идемпотентны: повторное выполнение не создаёт дубликатов.
- Неудачное извлечение (недоступная страница, пейволл, нестандартный формат) не теряет запись: она находится по URL, заголовку и заметке.

**Лимиты:**
- Загрузка страницы: таймаут 15 с, максимум 5 МБ, не более 5 редиректов.
- Документы: до 20 МБ (совпадает с лимитом скачивания файлов Telegram Bot API); таймаут разбора 60 с.

**Telegram:**
- Webhook отвечает `200` сразу, обработка — через очередь.
- Повторные события отбрасываются по `update_id`.
- Ответ `403` (бот заблокирован) → привязка отключается, отправка в Telegram прекращается.

**API:**
- Ошибки — ProblemDetails (RFC 9457); валидация — `400`.
- Чужая запись — `404`, а не `403`, чтобы не раскрывать её существование.

**Наблюдаемость:** Application Insights (структурированные логи, исключения), `/health`, алерт на рост числа упавших задач.

## 7. Безопасность

| Риск | Мера |
|---|---|
| **SSRF** (воркер скачивает URL пользователей) | Только `http`/`https`; DNS разрешается заранее, запрещены приватные, loopback и link-local адреса (включая `169.254.169.254`); каждый редирект проверяется заново |
| **XSS** из извлечённого контента | Храним текст, а не исходный HTML; Markdown в SPA санитизируется (DOMPurify); код выводится как текст |
| **Вредоносные файлы** | Приватный Blob-контейнер, скачивание только через API с `Content-Disposition: attachment`, проверка типа по сигнатуре |
| **Утечка данных между пользователями** | Глобальный фильтр по `user_id` + Row-Level Security + тесты изоляции |
| **Сессии и CSRF** | Cookie `HttpOnly`, `Secure`, `SameSite=Lax`, anti-forgery для изменяющих запросов; API-токены только через `Authorization: Bearer` |
| **Секреты** | Key Vault через Managed Identity; вход в PostgreSQL по Entra ID (Managed Identity), без паролей; TLS обязателен |
| **Сетевой доступ к БД** | Firewall PostgreSQL — только исходящие IP App Service; Private Endpoint (~+$7/мес) — позже при необходимости |
| **Злоупотребления** | Rate limiting ASP.NET Core на пользователя и IP; отдельные лимиты на вход, webhook и загрузку |
| **Потеря данных** | Автобэкапы PostgreSQL (7 дней), soft delete в Blob Storage |

## 8. Тестирование

**Unit (xUnit):**
- Извлечение контента на эталонных HTML/PDF/DOCX из фикстур.
- Разбор сообщений бота: ссылки, хэштеги, подписи.
- Сборка дайджеста: отбор записей, часовые пояса.
- SSRF-валидатор: приватные адреса, IPv6, IP в десятичной записи (`http://2130706433`), редирект на внутренний адрес.

**Интеграционные (WebApplicationFactory + Testcontainers с той же версией PostgreSQL, что в Azure):**
- Поиск: морфология («очереди» → «очередь», «messages» → «message»), ранжирование (совпадение в заголовке выше, чем в тексте), фильтры, подсветка.
- Изоляция: для каждого эндпоинта пользователь B запрашивает ресурсы пользователя A → `404`; поиск и экспорт не возвращают чужие записи; RLS проверяется отдельно, в обход EF-фильтра.
- Очередь: два воркера не берут одну задачу; повторы и задержки; восстановление после истёкшего захвата.
- Миграции применяются на чистую базу.
- Внешние зависимости: WireMock.Net (веб-страницы, Telegram API), Azurite (Blob), фейковый отправитель email.

**Фронт:** Vitest + React Testing Library для компонентов; Playwright smoke: вход → сохранить ссылку → дождаться `ready` → найти поиском → отметить прочитанной.

## 9. Поставка

- **Инфраструктура как код:** Bicep (App Service, PostgreSQL, Storage, Key Vault, ACS, App Insights).
- **CI/CD (GitHub Actions):**
  - pull request — сборка и все тесты;
  - `main` — сборка SPA → публикация .NET → EF migrations bundle → деплой в App Service.
- **Окружения:** `prod` + локальная разработка (docker compose: PostgreSQL + Azurite).

## 10. Развитие после первой версии

- Смысловой (гибридный) поиск: `pgvector` + таблица `item_chunks`.
- Вынос Ingestion в отдельный сервис (Container Apps) при росте нагрузки.
- Private Endpoint для PostgreSQL.
- Браузерное расширение для сохранения в один клик.
- Переход на Azure AI Search, если качества поиска PostgreSQL окажется недостаточно.
